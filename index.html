Attack surface

How AI systems actually get breached

Documented attack classes, not theoretical scenarios. Each maps to the OWASP LLM Top 10.

OWASP LLM01

Direct Prompt Injection

Attacker-supplied text in user input overrides or appends to the model's system prompt, redirecting its behavior. No special access is required beyond the normal user interface of the application.

Impact — Exfiltration of system instructions, impersonation of authorized roles, generation of policy-violating content under the application's identity.
OWASP LLM02

Indirect Prompt Injection

Adversarial instructions embedded in documents, emails, or web pages retrieved at inference time execute within the model's trust context — without any direct attacker interaction with your system.

Impact — Cross-user data leakage, privilege escalation in multi-tenant RAG applications, silent exfiltration of data from retrieved documents.
OWASP LLM06

Insecure Agentic Tool Use

An LLM agent granted tool-calling permissions executes attacker-influenced instructions without per-action authorization checks. The agent acts as an unwitting proxy for the attacker within your infrastructure.

Impact — Lateral movement across connected systems, irreversible API calls (data deletion, external data transfer) under the application's credentials.
OWASP LLM03 / LLM04

Model Supply Chain Compromise

Unsafe serialization formats (Pickle) or poisoned fine-tuning datasets introduce backdoor behavior before a model reaches production. The compromise occurs before deployment, inside the ML pipeline.

Impact — Persistent backdoors that survive model updates and standard pre-deployment checks; targeted behavioral triggers activated by specific inputs in production.

Methodology

How an engagement works

[ADD: typical timeline, e.g. "Most engagements run 1–2 weeks from scoping call to report delivery."]

01
Scoping call

We define the target system, attack surface, testing window, rules of engagement, emergency stop procedures, and points of contact. Written authorization is issued before any testing begins.

02
Threat modeling

I map your system's data flows, trust boundaries, tool permissions, and integration points to identify the highest-probability attack paths specific to your stack — before active testing begins.

03
Adversarial testing

Systematic probing across the agreed scope: prompt injection variants, guardrail bypass techniques, RAG manipulation, agentic tool abuse, and supply chain analysis — all within the written authorization boundary.

04
Finding documentation

Each vulnerability is documented with exact reproduction steps, severity (OWASP LLM Top 10 reference), business impact analysis, and specific remediation guidance your engineering team can act on immediately.

05
Report delivery & walkthrough

Full written report with executive summary and technical appendix. A one-hour walkthrough session is included to review findings with your team and answer questions about remediation priorities.

06
Remediation review (optional)

A follow-up assessment to verify that your fixes hold under the same attack conditions used to find the original vulnerabilities. Available as an add-on to any engagement.

Professional standards

How I work safely

These are operational commitments, not marketing copy. Every engagement follows this structure.

Written authorization

Testing begins only after written authorization is received and countersigned. No testing occurs on systems not explicitly listed in the authorization document.

Scope boundary enforcement

Testing is confined to the agreed target systems. Any out-of-scope system found to be vulnerable is documented and disclosed to you, not tested further without additional authorization.

Signed rules of engagement

A signed ROE document defines permitted techniques, testing windows, emergency stop procedures, and designated contacts before any work begins. Available for review before you commit.

NDA before discussions

A non-disclosure agreement is signed before any discussion of your systems, architecture, or business context. Available on request before the first scoping call.

Data handling & deletion

All data accessed during an engagement — logs, prompts, model responses — is stored only as needed to produce the report. At engagement close, all copies are deleted and confirmed in writing.

Responsible disclosure

Out-of-scope vulnerabilities in third-party products are reported to the vendor under coordinated disclosure — not publicly released during your engagement. See security.txt.
